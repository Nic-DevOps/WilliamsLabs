Monitoring VM & Ansible Automation

Stand up a general-purpose Debian 13 VM to run Prometheus/Grafana and connect it to Cisco Modeling Labs (CML), then convert the build into an Ansible playbook so it can be destroyed and recreated reproducibly.

Host: Debian 13 (trixie), VMware Workstation Network: VMnet10 host-only, 192.168.100.0/24 Status: In Progress

Overview

Every lab from 07 onward depends on this VM. It runs in VMware Workstation alongside a separate Cisco Modeling Labs (CML) VM, and is currently treated as general-purpose — later split into dedicated monitoring vs. provisioning VMs as the environment grows.

Build order

  • SSH

Monitoring (Prometheus/Grafana) was prioritized ahead of automation tooling (Ansible/Terraform) so the lab had visibility into itself as early as possible.

CML connectivity

The CML controller runs two NICs: ens160 on NAT/bridge0 for management, and ens32 on a custom bridge mapped to the host-only VMnet10 (192.168.100.0/24). Getting the monitoring VM talking to CML lab nodes required rebuilding CML's bridge1 in the System Administration Cockpit — disabling IPv4/IPv6 on the bridge before adding ens32 as a member port, then pointing CML's External Connector at bridge1.

Toward reproducibility

The plan is to capture this build — packages, users, systemd units, configs — as an Ansible playbook, so the VM becomes disposable rather than hand-maintained: destroy it, rerun the playbook, get an identical monitoring host back. A second VM is planned to run Terraform + Ansible for provisioning lightweight Linux/Windows systems that also tie into CML, separating "watches the lab" from "builds the lab."
