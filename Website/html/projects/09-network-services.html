Network Services (DHCP) Lab

Deploy a centralized DHCP server at HQ, configure DHCP relay for remote-site VLANs, enable SSH management fleet-wide, and extend Prometheus/Grafana monitoring to Site A and Site B.

DHCP server: Kea DHCPv4, 10.10.50.22 Sites monitored: HQ, Site A, Site B Status: In Progress

Overview

Building on the OSPF-routed multi-site network from Lab 08, this lab centralizes DHCP at HQ using Kea, relays requests from Site A and Site B over the existing WAN, standardizes SSH management across every switch and router, and extends the monitoring stack from Lab 07 to cover all three sites instead of just HQ.

SSH management

username admin privilege 15 secret <PASSWORD>
ip domain-name williamslabs.local
crypto key generate rsa modulus 2048
ip ssh version 2

line vty 0 4
 login local
 transport input ssh

DHCP design

The DHCP server sits in the HQ NET-MGMT VLAN on a static IP; each client VLAN receives addresses dynamically via relay.

SiteVLANNetworkGateway
HQ10 / 30 / 4010.10.x.0/2410.10.x.1
Site A10 / 30 / 4010.20.x.0/2410.20.x.1
Site B10 / 30 / 4010.30.x.0/2410.30.x.1

Relay is configured on the Layer 3 gateway for each DHCP-enabled VLAN — the HSRP virtual IP where HSRP is in play:

interface Vlan10
 ip helper-address 10.10.50.22

Monitoring extended multi-site

Prometheus targets are now organized by site label (HQ, Site A, Site B, Hub) so Grafana can filter the dashboard with a site variable instead of one flat device list:

- targets: ["10.20.50.1"]
  labels:
    site: "Site A"
    device: "SiteA-CoreSW01"

Verification

A client on each site pulled an address from the correct VLAN-specific pool (verified against DHCP server leases), and show running-config interface Vlan10 confirmed the correct ip helper-address on each gateway.

What's next

Planned: DNS, DHCP high availability, DHCP snooping, and pulling addressing/inventory from NetBox instead of hand-maintained tables.
