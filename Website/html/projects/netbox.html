NetBox — Infrastructure Source of Truth

NetBox is up and running in the lab as a production service and is the source of truth for device inventory and IP address management. The integrations with automation and monitoring are still to come.

OS: Debian 13 Stack: NetBox 4.6.8 · Nginx · Gunicorn · PostgreSQL 17 · Redis 8.0.2 Status: Running, integrations in progress

Overview

NetBox runs on its own Debian VM as the infrastructure source of truth for the lab: device inventory (DCIM) and IP address management (IPAM). It is up and running as a permanent service and is in day-to-day use. The goal is for NetBox to feed the automation and monitoring tools, so that device lists don't have to be kept by hand in several places.

How it got up and running

  1. Base install. Built a Debian 13 VM with a dedicated netbox service account. Installed PostgreSQL 17 and Redis, and installed NetBox 4.6.8 into a Python virtual environment.
  2. Configuration. Set the database and Redis connections (one Redis database for tasks and one for the cache), a generated SECRET_KEY, and API_TOKEN_PEPPERS for API tokens.
  3. Initialisation. Ran the database migrations, created the admin account, and collected the static files.
  4. Smoke test. Checked that login and the dashboard worked using Django's development server, then turned DEBUG back off.
  5. Production deployment. Replaced the development server with Gunicorn behind an Nginx reverse proxy, with systemd starting the service at boot.
  6. Population. Entered the lab's sites, devices, VLANs, prefixes and infrastructure addresses. DHCP clients were left out because their addresses change. A scoped API token now gives scripted access through the REST API.

Lessons learned

  • In NetBox 4.6, API_TOKEN_PEPPERS must be a dictionary ({1: '...'}). A plain string fails with ImproperlyConfigured.
  • The first migration failed with permission denied for schema public. PostgreSQL 15 and later no longer let every user create objects in the public schema, so the fix was to make the netbox role the owner of the database and the schema.
  • Django's runserver is only for a quick test. NetBox needs a proper WSGI server and reverse proxy to run as a permanent service.

Still to do

  • Background worker. Enable and start the netbox-rq service. The web interface and API work without it, but jobs such as custom scripts, reports and webhooks won't run until it is running.
  • Ansible. Build the Ansible inventory from the NetBox API.
  • Terraform. Use NetBox data to drive provisioning.
  • Monitoring. Find Prometheus/Grafana targets through NetBox instead of a hand-kept list.
